## Introduction

Large Language Models (LLMs) such as ChatGPT and GPT-4 have demonstrated remarkable capabilities in generating source code from natural language descriptions. Yet despite their impressive fluency, the code they produce is far from reliable. Studies have shown that LLM-generated code often contains subtle logical errors, fails edge cases, or simply does not meet the functional requirements specified in the prompt.

The dominant approach to addressing this problem has been **self-correction** — feeding the LLM its own erroneous output and asking it to try again. While intuitive, this strategy has fundamental limitations: the model tends to repeat the same types of mistakes, and there is no systematic mechanism guiding the correction process toward genuinely better solutions.

In this work, published at **EuroGP 2024** (part of the EvoStar conference), we proposed a fundamentally different approach: rather than relying on the LLM to fix its own code, we treat the generated code as a starting point and apply **Genetic Improvement (GI)** — a search-based software engineering technique — to evolve it toward correctness.

## The Core Idea: Code as Evolvable Material

Genetic Improvement is inspired by biological evolution. Just as natural selection operates on genetic variation to produce organisms better adapted to their environment, GI operates on program variants to produce software better adapted to its specification. The key insight is that LLM-generated code, even when incorrect, is typically *close* to a correct solution — it captures the overall structure, uses appropriate data types, and often implements the right algorithmic approach. What it needs is targeted refinement, not wholesale rewriting.

Our approach combines GI with **Grammatical Evolution (GE)**, a grammar-based evolutionary technique that constrains mutations to produce only syntactically valid programs. This is critical: random mutations applied to source code almost always produce programs that do not even parse, let alone execute correctly. By defining a formal grammar that describes the space of valid modifications, we ensure that every mutant in the evolutionary search is at least syntactically well-formed.

## The Three-Phase Pipeline

Our methodology consists of three phases that transform raw LLM output into improved code:

### Phase 1: Code Extraction and Analysis

The first phase takes the raw text output from an LLM and extracts executable Python code. This is less trivial than it sounds — LLMs embed code within explanatory text, markdown formatting, and sometimes produce multiple code blocks. We developed extraction routines that reliably isolate the intended program from surrounding text.

Once extracted, the code undergoes **Abstract Syntax Tree (AST) analysis**. Python's `ast` module parses the code into a tree representation, allowing us to identify all syntactic elements present: variable types, control structures, function definitions, operators, and library calls.

### Phase 2: Dynamic Grammar Specialization

This is one of the key contributions of our work. Rather than using a single, universal grammar for all programs, we **dynamically generate a specialized BNF (Backus-Naur Form) grammar** from the AST analysis of each LLM-generated program.

The rationale is straightforward: if the LLM's code uses only integer variables and `for` loops, there is no benefit in exploring mutations that introduce floating-point arithmetic or `while` loops. By restricting the grammar to constructs already present in the code (or closely related ones), we dramatically reduce the search space while preserving the ability to make meaningful improvements.

The specialized grammar is automatically constructed by mapping AST node types to grammar production rules. Each program thus has its own tailored mutation space — a form of intelligent search space design that leverages the LLM's output as prior knowledge.

### Phase 3: Evolutionary Search

With the grammar in hand, we apply Grammatical Evolution using the **PonyGE2** library. The evolutionary process operates as follows:

- **Population**: 1,000 individuals, each representing a variant of the original LLM code
- **Generations**: up to 100 evolutionary generations
- **Selection**: Tournament selection with size 2
- **Crossover**: Variable one-point crossover (probability 0.75)
- **Mutation**: Integer flip mutation (probability 0.05)
- **Fitness**: The proportion of test cases from the PSB2 benchmark that each variant solves correctly

Each individual in the population is a sequence of integers (a genotype) that gets mapped through the grammar to produce a concrete program (the phenotype). Crossover and mutation operate on the integer sequences, while the grammar ensures the resulting programs are always syntactically valid.

## Experimental Setup

We evaluated our approach on **25 program synthesis problems** from the **PSB2 (Program Synthesis Benchmark 2)** suite. Each problem specifies an input-output transformation — for example, computing the greatest common divisor, sorting a list, or processing strings — and comes with 1,000 test cases for fitness evaluation.

We tested five LLMs spanning a range of capabilities:

- **GPT-4**: OpenAI's most capable model at the time
- **ChatGPT (GPT-3.5-turbo)**: The widely deployed conversational model
- **LLaMA-2 13B**: Meta's open-source model
- **Alpaca-13B**: A fine-tuned variant of LLaMA
- **Alpaca-7B**: A smaller fine-tuned model

For each LLM and each problem, we generated initial code using a standardized prompt, then applied our GI pipeline. Each experiment was repeated 30 times to ensure statistical robustness, and we used the Wilcoxon signed-rank test to assess significance.

## Results

The results were clear and consistent:

**GI improved the code of every LLM tested**, with statistically significant improvements (p < 0.001) across the board. The magnitude of improvement varied by model — smaller, less capable models like Alpaca-7B saw the largest relative gains, suggesting that GI is particularly effective at compensating for limited model capacity.

Specific highlights include:

- **Alpaca-7B**: The weakest initial performer showed dramatic improvement through GI, with many problems going from zero test cases passed to partial or complete correctness.
- **GPT-4**: Even the strongest model benefited from GI refinement, though the gains were smaller in absolute terms (since GPT-4's initial code was already relatively good).
- **Cross-model consistency**: The improvement was not limited to specific problem types — GI helped across arithmetic, string manipulation, list processing, and other categories.

**Importantly, GI consistently outperformed LLM self-correction.** When we compared our approach against simply prompting the LLM to fix its own errors (with access to failing test case information), the evolutionary approach produced better final code. This makes sense: self-correction is constrained by the model's own biases and blind spots, while GI explores a much broader space of possible modifications.

## Why This Works

The effectiveness of our approach rests on three complementary factors:

1. **LLMs provide good starting points.** The generated code is usually structurally sound — the right functions are called, the right data structures are used, the overall algorithm is reasonable. This means the search space around the LLM's output contains many viable improvements.

2. **Grammar specialization focuses the search.** By tailoring the mutation grammar to each specific program, we avoid wasting computational effort exploring irrelevant regions of the code space. The search is concentrated where improvements are most likely to be found.

3. **Evolutionary search is robust.** Unlike greedy repair strategies that can get stuck in local optima, the population-based search of GE maintains diversity and can combine partial improvements from different individuals through crossover.

## Implications

This work opens several important directions:

For **practitioners**, it suggests that LLM code generation pipelines can be significantly enhanced by adding a post-processing optimization stage. Rather than accepting LLM output as-is or relying on expensive re-prompting, a GI stage can systematically improve code quality.

For **researchers**, the dynamic grammar specialization technique is applicable beyond this specific setting — any scenario where GI is applied to programs with known structural characteristics could benefit from a similar approach to search space reduction.

For the **broader field**, this work demonstrates that the strengths of neural and evolutionary approaches are complementary: LLMs excel at generating plausible code quickly, while evolutionary methods excel at systematic refinement toward precise specifications.
