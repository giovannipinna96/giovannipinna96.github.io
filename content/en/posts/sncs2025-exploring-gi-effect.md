{{< summary-box title="Abstract" >}}
This work extends our EuroGP 2024 study on improving LLM-generated code through Genetic Improvement by introducing three key enhancements: lexicase selection to preserve specialist solutions, 10% down-sampling for computational efficiency, and a refined fitness function (F_E) that provides partial credit rather than binary pass/fail evaluation. We evaluate the enhanced pipeline on four LLMs — GPT-4, ChatGPT, Code Llama 7B, and LLaMA 3 8B — across three PSB2 benchmark problems. The approach achieves improvements in 11 out of 12 model-problem combinations, with the strongest relative gains observed on smaller, less capable models. This confirms that Genetic Improvement acts as a "capability amplifier," enabling open-source models to narrow the performance gap with larger proprietary alternatives. Published in SN Computer Science, Volume 6, Issue 7, 2025.

## Introduction

In our previous work at EuroGP 2024, we demonstrated that Genetic Improvement (GI) combined with Grammatical Evolution could systematically improve code generated by Large Language Models. That study established the fundamental viability of the approach. But several questions remained: Could the evolutionary search be made more effective with better selection strategies? Would the approach scale to newer, more capable models? And could we develop a more informative fitness function that provides finer-grained feedback to the evolutionary process?

This paper, published in **SN Computer Science (2025)**, addresses all three questions. We extended our original framework with **lexicase selection**, **down-sampling**, and a **refined fitness function**, then evaluated the enhanced pipeline on updated LLMs including Code Llama and LLaMA 3.

## Advancing the Selection Strategy

### The Limitations of Tournament Selection

Our original approach used tournament selection — a simple strategy where individuals compete in small random groups and the best one is selected for reproduction. While effective and computationally cheap, tournament selection has a well-documented limitation: it tends to favor generalists over specialists. An individual that performs moderately well across all test cases will be preferred over one that perfectly solves a subset of cases but fails on others.

In program synthesis, this is a significant drawback. A program variant that perfectly handles all integer edge cases but fails on negative numbers contains valuable partial solutions — but tournament selection may discard it in favor of a mediocre all-rounder.

### Lexicase Selection

**Lexicase selection** addresses this by evaluating individuals on test cases one at a time in a random order. The selection process starts with the full population, then iteratively filters out individuals that are not among the best on each successive test case. This naturally preserves specialists — individuals that excel on specific subsets of test cases survive even if their overall performance is unremarkable.

The theoretical advantages of lexicase selection for program synthesis are well-established in the evolutionary computation literature. Our contribution is demonstrating its effectiveness in the specific context of improving LLM-generated code.

### Down-Sampling for Efficiency

Lexicase selection becomes computationally expensive when the number of test cases is large (in our case, up to 1,000 per problem). **Down-sampling** addresses this by randomly selecting a subset of test cases for each generation. This reduces the computational cost per generation while maintaining selection pressure across the full test suite over time, since different subsets are sampled in each generation.

We experimented with a down-sampling rate of 10% — using only 100 of the 1,000 available test cases per generation — and found that this provided an excellent balance between efficiency and selection quality.

## A More Informative Fitness Function

Our original fitness function was the straightforward proportion of test cases passed. While intuitive, this binary per-test-case evaluation discards useful information. Consider a test case expecting the output `[1, 2, 3, 4, 5]`: a program outputting `[1, 2, 3, 4, 6]` (one element wrong) gets the same score as one outputting `"hello"` (completely wrong).

We developed a refined fitness function **F_E** that incorporates partial credit. Instead of just checking whether each output matches exactly, F_E measures how *close* each output is to the expected result. For numerical outputs, this might use absolute difference; for sequences, it might consider element-wise comparison. This finer-grained feedback helps the evolutionary process distinguish between "almost correct" and "completely wrong" variants, providing better gradient information for the search.

## Experimental Setup

We evaluated the enhanced pipeline on **three PSB2 problems** selected for their varying difficulty levels, using **four LLMs**:

- **GPT-4**: OpenAI's flagship model
- **ChatGPT (GPT-3.5-turbo)**: The widely-used conversational model
- **Code Llama 7B**: Meta's code-specialized model
- **LLaMA 3 8B**: Meta's latest generation open-source model

The evolutionary parameters were adjusted from our original study:

- **Population size**: 200 (reduced from 1,000, reflecting the more efficient selection strategy)
- **Generations**: up to 100
- **Lexicase selection** with **10% down-sampling**
- Each experiment repeated 30 times for statistical robustness

## Results

The enhanced pipeline achieved improvements in **11 out of 12 model-problem combinations** — a remarkably consistent result that validates both the lexicase selection strategy and the refined fitness function.

Key findings include:

**Strongest gains on smaller models.** Consistent with our previous work, the largest relative improvements were observed on less capable models. Code Llama 7B and LLaMA 3 8B — both significantly smaller than GPT-4 — showed the most dramatic gains from GI. This reinforces the finding that GI is particularly valuable as a "capability amplifier" for resource-constrained or open-source models.

**Lexicase selection preserves useful diversity.** The population dynamics under lexicase selection were qualitatively different from tournament selection. We observed greater phenotypic diversity maintained throughout the evolutionary run, with the population containing specialists for different subsets of test cases. This diversity translated into better exploration of the solution space.

**Down-sampling is effective.** Using only 10% of test cases per generation did not significantly degrade solution quality compared to using the full test suite, while substantially reducing computational cost. This makes the approach more practical for real-world deployment where evaluation budgets are limited.

**The refined fitness function helps most on harder problems.** For easy problems where the LLM's initial code is already close to correct, the binary fitness function and F_E produce similar results. But for harder problems where the initial code is far from correct, F_E provides meaningfully better gradient information, helping the search navigate toward solutions more efficiently.

## Comparison with Self-Correction

We again compared our GI approach against LLM self-correction, confirming and strengthening our previous findings. The evolutionary approach consistently outperformed self-correction, particularly on problems where the initial code had fundamental structural issues that the LLM's own correction mechanism could not overcome.

This is an important practical finding: it means that even for organizations already using self-correction in their LLM code generation pipelines, adding a GI stage provides additional, complementary improvements.

## Limitations and Future Directions

We identified several important limitations that guide future research:

1. **Oracle dependency**: Our approach requires test cases (or an oracle) to evaluate fitness. Problems without clear test suites are harder to address.
2. **Scalability**: The current evaluation is on relatively small programs. Scaling to larger, multi-file software engineering tasks remains an open challenge.
3. **LLM bias in grammar**: The dynamically generated grammar inherits structural biases from the LLM's output, potentially limiting the space of discoverable improvements.

These limitations motivate ongoing work on grammar-free GI approaches, fitness approximation techniques, and integration with larger-scale software engineering workflows.
